# /invent 실행 절차

입력: `$ARGUMENTS` (질문 또는 아이디어). 비어 있으면 대표님께 무엇을 조사할지 한 줄로 물어본다.

## 0. 준비

1. 오늘 날짜와 주제로 폴더를 만든다: `runs/YYYY-MM-DD-<주제 짧은 영문 슬러그>/`
2. **모드를 정한다.** 입력에 `--특허`가 있으면 특허 모드, 없으면 **실용 모드(기본)**. 실용 모드는 제품·리뷰·가격·원가 우선, 특허는 간단 확인(KIPRIS 10회·Google Patents 5건·청구항 도구 3건). 특허 모드는 기존 해법 담당의 특허 조사를 풀로(KIPRIS 20회·청구항 도구 20건).
3. **야심 수준을 정한다.** 입력에 `--야심 부속|신제품|범주`가 있으면 그것, 없으면 **신제품(기본)**. 뜻과 제작 문턱은 `rubric/점수표.md` "야심 수준" 표. 부속 = 기존 물건에 붙이는 소형 부속(예전 기본값), 신제품 = 기존 범주 안의 새 제품(전자·앱 허용), 범주 = 새 범주·시스템. 대표님께 되묻지 않는다.
4. 그 폴더에 `00-질문.md`를 쓴다: 원래 질문, 총괄이 해석한 질문, 1단계부터인지 2단계부터인지, **모드(실용/특허)**, **야심 수준(부속/신제품/범주)**, Aside 사용 여부. 입력에 "Aside 사용"이라는 말이 있을 때만 "Aside 사용", 그 외 전부 "사용 안 함".
5. 판단 기준: 입력이 "어떤 제품을 만들까"류(영역만 있음)면 1단계부터. 입력이 구체적 제품·기능이면 2단계부터.
6. `sources/출처안내서.md`와 `rubric/점수표.md`를 읽는다. 담당 브리핑마다 모드·야심 수준·상한·"Aside 사용 안 함"을 명시한다.

## 1단계. 탐색 (넓은 질문일 때만)

1. 영역 분할: 주제를 생활 장면 기준으로 5~8개 영역으로 쪼갠다. 예) 욕실 → 샤워, 세면·양치, 수납, 청소·곰팡이, 노인·안전, 아동, 환기·습기, 배수.
   `01-영역.md`에 영역 목록과 쪼갠 이유를 쓴다.
2. 불편 발굴 담당(`pain-finder`)을 **영역마다 하나씩, 동시에** 띄운다. 각 호출에 넘길 것: 영역 이름, 주제, 저장 경로(`01-불편-<영역>.md`), 1단계 상한(웹검색 10회, Aside 금지).
3. 결과를 모아 `rubric/점수표.md`의 1단계 점수를 매긴다.
   - 먼저 야심 수준의 **제작 문턱**을 통과하는지 본다(1단계는 총괄 추정). 못 넘으면 "문턱 탈락"으로 순위표에 남기되 점수는 매기지 않는다. 부속 수준으로 내리면 넘는 불편은 "부속으로는 가능"이라고 표시한다.
   - 통과한 불편마다 빈도·강도·미해결도·근본성을 1~5로 매기고 근거 등급을 붙인다. 미해결도는 제품 수가 아니라 상위 제품 리뷰의 만족도로 잰다. 근본성은 같은 원인을 공유하는 불편 수로 잰다(같은 원인이면 불편을 합쳐 하나의 후보로 만들고 합친 근거를 적는다).
   - 점수가 같으면 근본성 → 근거 등급 → 강도 순으로 위.
   `02-점수표.md`에 전체 순위표를 쓴다(양식은 점수표의 "1단계 순위표 양식").
4. 상위 3개 후보를 뽑아 대표님께 보여준다. 형식:
   - 후보 이름 한 줄, 누구의 어떤 불편인지, 점수, 근본성, 근거 등급, 왜 1위인지(또는 왜 밀렸는지) 두 줄.
   - 상위 3개가 전부 근본성 1~2점이면 "이 영역에선 부속밖에 안 나온다"고 말하고 근본성 4 이상 최고점 하나를 4번째로 함께 보여준다.
   - "하나를 고르시거나 '전부'라고 하시면 심층으로 갑니다."
5. **여기서 멈추고 답을 기다린다.** 답 없이 2단계로 넘어가지 않는다.

## 2단계. 심층 (후보마다)

후보 하나당 아래 순서. "전부"면 후보 세 개를 차례로. 후보가 여럿이면 `A-<이름>/`, `B-<이름>/` 폴더를 만들어 그 안에 저장한다.

1. **원인 분석(`cause-analyst`)·기존 해법 조사(`solution-scout`)·왜 지금(`why-now`)을 동시에** 띄운다. 넘길 것: 후보 설명, 대상 불편과 불편 파일 경로(같은 원인을 공유하는 다른 영역 파일 포함), 저장 경로(`05-원인분석.md`, `10-기존해법.md`, `11-왜지금.md`), 모드, 야심 수준, 2단계 상한(원인 분석 웹검색 10회, 나머지 20회). 실용 모드 브리핑에는 "특허는 간단 확인만, 필수 산출물은 리뷰 출처 2곳 이상·공통 불만 3가지·가격대 구간표·판매량 대리 지표"를 적는다. 원인 분석에는 "해법 제안 금지, 사실은 출처·추론은 가설 표시"를 적는다.
2. 세 결과를 읽고, 각 결과의 "추가 조사 요청" 블록을 본다. 요청이 있으면 `source-digger`를 요청당 하나씩 띄운다(후보당 최대 4회). 결과는 `12-보조-<출처>.md`에 저장시키고, 해당 담당 결과 파일 끝에 "보조 조사 반영" 절을 총괄이 덧붙인다.
3. **발상(`ideator`, 개방 모드)**을 띄운다. 넘길 것: 모드 "개방", 야심 수준, `05-원인분석.md`·`01-불편-*.md`·`10-기존해법.md`·`11-왜지금.md` 경로, 저장 경로(`15-발상.md`), 검색 0회. 후보 15~20개를 네 층위(부속/개선/새 범주/시스템)로 낸 뒤 문턱을 적용해 3~5개와 추천 순서를 돌려받는다.
4. 총괄이 `15-발상.md`의 추천 순서를 읽고 **제안 하나를 고른다.** 기본은 발상 담당의 1순위. 총괄이 다른 것을 고르면 이유를 `00-질문.md` 끝에 한 줄 적는다. 대표님께 묻지 않는다(묻는 지점은 후보 선택과 최종 전달 두 곳뿐). 고르지 않은 제안은 최종 보고서 "고른 제안과 대안" 절에 한 줄씩 남긴다.
5. **디자인 제안(`design-proposer`)과 구현·원가(`build-cost`)를 동시에** 띄운다. 넘길 것: 고른 제안 번호와 `15-발상.md` 경로, `05-원인분석.md` 경로, 불편 결과, 기존 해법 결과 경로(차별점을 알아야 함), 야심 수준, 저장 경로(`20-디자인.md`, `21-구현원가.md`). 구현·원가에는 "제작 문턱 세 숫자(금형·초기비 합계, MOQ, 인증 종류·비용)를 야심 수준 문턱과 대조해 신호등"을 반드시 요구한다. 디자인에는 "고른 제안의 원리를 바꾸지 말고 구체화할 것, 어느 원인 노드를 없애는지 명시"를 요구한다.
6. 검증(`verifier`)을 띄운다. 넘길 것: 이 후보 폴더의 모든 결과 파일 경로. 저장 경로 `30-검증.md`. 검증은 먼저 `tools/출처확인.py`를 돌려 `29-출처확인.md`를 만들고, 그 위에서 주장별 판정을 한다. "가설" 표시 문장은 사실 대조 대상이 아니고, 표시 없이 쓴 추론은 "출처 없음"으로 잡는다. 검증이 "근거 불충분"으로 표시한 주장은 최종 보고서에서 등급을 내리거나 뺀다.
7. `templates/최종보고서.md` 양식대로 `40-최종보고서.md`를 쓴다. 모든 항목에 근거 등급을 붙인다. 신호등은 점수표 2단계의 일곱 항목(원인 해결·제작 문턱 포함). "검증해야 할 것" 절은 가정표(가치/사용/사업/구현 × 중요도 × 근거)로 반드시 채우되 원인 분석의 "참이어야 하는 가정"과 발상의 "가장 먼저 틀릴 가정"을 먼저 넣는다.

## 3. 전달

대표님께 최종 보고서 경로와 아래 요약을 준다:
- 한 줄 결론 (누구의 어떤 불편을 무엇으로 해결, 왜 지금)
- 고른 제안의 층위(부속/개선/새 범주/시스템)와 원인 해결 신호등, 고르지 않은 제안 한 줄씩
- 가장 큰 위험 하나
- 다음에 사람이 직접 확인해야 할 것 3개
- 상한에 걸려 못 한 조사가 있으면 그 목록

## 상한과 중단

- 상한은 `CLAUDE.md`의 숫자를 따른다. 담당에게 넘길 때 숫자를 명시한다.
- 담당이 로그인 화면·캡차·접근 차단을 보고하면 그 출처는 건너뛰고 "미확인"으로 두고 진행한다. 대표님께는 전달 시점에 한 번에 알린다.
- Aside는 기본 사용 안 함. `00-질문.md`에 "Aside 사용"이 없으면 담당은 시도조차 하지 않고, 쿠팡·아마존·알리바바는 검색 스니펫 수준으로만 적는다. "Aside 사용" 실행에서 도구가 안 보이거나 402·미실행 오류면 그 출처는 건너뛰고 전달 시점에 알린다.
- 실용 모드에서 특허 상한(KIPRIS 10회·Google Patents 5건)에 닿으면 "특허 간단 확인"으로 끝내고 보고서 특허 여지 신호등은 "같은 물건의 살아 있는 등록 건 유무"로만 매긴다.
- KIPRIS MCP 도구(`mcp__kipris__*`)가 안 보이거나 키 오류를 내면 기존 해법 담당은 Google Patents만 쓰고, 전달 시점에 "KIPRIS MCP 미설정"을 알린다.
- 1단계 결과 파일에서도 등급 기준은 `rubric/점수표.md` 하나다. 담당이 다른 기준을 적어 왔으면 총괄이 점수표를 매길 때 다시 센다.
- 발상 담당이 문턱을 통과하는 제안을 하나도 못 내면 멈추고 대표님께 "야심 수준을 내리거나 다른 후보로"를 묻는다. 이것은 예외적인 세 번째 질문 지점이다.
