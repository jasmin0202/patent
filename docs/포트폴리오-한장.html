문제 LLM에게 시장 조사를 시키면 생기는 일

그럴듯한 문장은 나오지만 어디서 왔는지 모른다. 없는 특허번호를 만들고, 댓글 한 개를 시장 전체의 불만처럼 쓰고, 출처 링크가 죽어 있어도 모른다. 이 셋을 프롬프트가 아니라 구조로 막는 것이 목표였다.

흔한 실패이 시스템의 장치
출처 없는 주장출처 없는 문장은 "미확인" 등급. 보고서 모든 줄에 등급이 붙는다
지어낸 특허번호검색 결과·API 응답에서 복사한 번호만 허용. 검증 단계에서 번호와 링크를 기계 대조
과장된 일반화독립 출처 3개 이상이어야 "확인됨". 같은 글의 댓글·다른 URL은 1개로 센다
죽은 링크 · 끝없는 조사모든 URL을 실제로 열어 판정. 담당별 검색 횟수 상한

구조 역할 7개, 사람은 두 번만 개입

담당은 서로를 모르고 결과는 파일로만 오간다. 서브에이전트는 서브에이전트를 못 띄우므로 보조 조사원은 총괄이 대신 띄운다.

설계 결정 왜 그렇게 했나

  • 총괄은 조사하지 않는다. 검색 결과가 컨텍스트를 채우면 판단이 흐려진다. 총괄은 쪼개고, 띄우고, 줄 세우는 일만.
  • 근거 등급은 내릴 수만 있다. 담당이 "확인됨"이라 써도 검증이 독립 출처 3개를 못 세면 "추정". 담당마다 기준을 달리 적는 일이 실제로 생겨 기준을 한 파일로 고정했다.
  • 우회하지 않는다. 로그인·캡차·차단은 멈추고 "막힌 출처"에 적는다. 로그인 사이트는 Aside 브라우저로 읽기만.

어려웠던 점과 해결

  • 특허번호 이중 집계. 본문 번호와 링크 안의 번호를 같이 세는 버그를 단위 테스트가 잡았다. URL을 떼어낸 줄에서만 번호를 찾게 고쳤다.
  • 한글 URL. 경로에 한글이 있으면 ASCII 오류로 "닫힘"이 됐다. 퍼센트 인코딩과 IDNA 변환을 넣어 실제로 열리게 했다.
  • "로그인" 오탐. 정상 글도 메뉴의 "로그인" 때문에 차단으로 잡혔다. 제목에 단서가 있거나 본문이 아주 짧을 때만 차단 의심으로 좁혔다.
  • 외부 코드와 비밀값. 제3자 MCP 서버는 소스를 읽고 저장소 밖에 두었고, API 키는 환경변수로만. CI가 키 패턴을 검사한다.

배운 것

LLM 시스템의 신뢰도는 모델이 아니라 검증을 어디에 두느냐에서 나온다. "출처 없으면 미확인" 규칙 하나와 그것을 기계로 확인하는 도구가, 프롬프트를 다듬는 것보다 결과를 더 많이 바꿨다.
